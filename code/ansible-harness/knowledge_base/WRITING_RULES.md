# knowledge_base 작성 규칙

이 문서는 **AnsibleHarness AI/RAG v1이 실제로 더 잘 검색하고 더 덜 헷갈리도록** `knowledge_base/` 문서를 작성하는 규칙을 정리한 문서입니다.

이 문서의 목적은 세 가지입니다.

1. 문서가 **검색 의도와 다른 도메인으로 새는 문제**를 줄입니다.
2. 한 문서가 너무 많은 주제를 섞어서 **chunk 품질이 떨어지는 문제**를 줄입니다.
3. 문서 제목/첫 문단/헤딩 구조를 정리해서 **질문과 문서가 더 잘 매칭**되도록 만듭니다.

> 이 규칙은 현재 저장소의 실제 구현을 기준으로 작성되었습니다. 현재 RAG는 `knowledge_base/` 아래 파일만 읽고, `doc_group`은 **폴더 경로**에서 결정되며, 지원 파일 형식도 제한되어 있습니다.

---

## 1. 이 문서가 적용되는 범위

- 적용 대상: `knowledge_base/` 아래에 새로 추가하거나 수정하는 문서
- 적용 대상 형식: `.txt`, `.md`, `.html`, `.yml`, `.yaml`, `.py`
- 적용 제외: `docs/`, `backend/`, `frontend/`, 루트 메모 문서, 임시 실험 파일

`knowledge_base/README.md`와 이 문서가 충돌하면, **현재 운영 기준은 README를 우선**하고 이 문서를 같이 갱신합니다.

---

## 2. 현재 시스템이 문서를 보는 방식

현재 시스템은 문서를 사람처럼 이해하지 않고, 아래 제약 안에서 검색합니다.

- `doc_group`은 문서 내용이 아니라 **첫 번째 폴더 이름**으로 결정됩니다.
  - 예: `knowledge_base/coding_rules/foo.md` → `doc_group = coding_rules`
- 문서는 확장자별로 쪼개져 chunk가 됩니다.
  - `.md`, `.html`: 대략 1400자 단위
  - `.py`: 대략 1200자 단위
  - `.yml`, `.yaml`: 대략 1100자 단위
- 검색은 현재 하이브리드 검색이 아니라 **벡터 검색 + 제한적인 도메인 필터** 중심입니다.
- 그래서 **폴더 이름이 곧 도메인 힌트**가 되고, **첫 문단과 초기 헤딩이 검색 품질에 큰 영향**을 줍니다.

즉, 지금은 문서를 자유롭게 쓰는 것보다 **검색 친화적으로 명확하게 쓰는 것**이 더 중요합니다.

---

## 3. 가장 중요한 3가지 원칙

### 3.1 한 파일에는 한 핵심 주제만 담습니다

좋은 예

- `파이선가이드.md` → 파이썬 스타일 가이드만 설명
- `nginx_설치_예제.md` → Nginx 설치 예제만 설명

나쁜 예

- 한 파일 안에서 Python 스타일 규칙 + Ansible 운영 팁 + 예제 코드까지 모두 섞음

문서가 길어지는 것 자체는 괜찮지만, **주제가 바뀌면 파일을 분리**해야 합니다.

### 3.2 폴더 의미와 실제 내용이 반드시 일치해야 합니다

현재 `doc_group`은 폴더명으로만 정해집니다. 그래서 **폴더를 잘못 선택하면 검색이 잘못됩니다.**

- `ansible/` → Ansible 플레이북, role, task, 인벤토리 운영 문서
- `python/` → Python 스타일 가이드, 구현 규칙, 코드 품질 문서

#### 실제 반례

`knowledge_base/python/Ansible Playbook 계층 구조.md`는 현재 제목부터 `# Ansible Playbook 계층 구조 상세 설명`으로 시작합니다. 이 문서는 내용상 Ansible 문서인데 `python/`에 있어서 검색 누수의 원인이 됩니다.

이런 문서는 **내용에 맞는 폴더로 이동하거나 문서를 분리**해야 합니다.

### 3.3 제목과 첫 문단에서 문서 정체를 바로 선언합니다

문서 첫 부분만 읽혀도 “이 문서가 무엇인지” 알 수 있어야 합니다.

좋은 예

- 첫 줄 또는 첫 문단에 문서 정체가 바로 드러남
- 실제 사용자가 검색할 키워드가 초반에 포함됨

예시:

```md
# PEP 8 – 파이썬 코드 스타일 가이드 통합 문서

이 문서는 Python / 파이썬 코드 스타일, PEP 8, 들여쓰기, 네이밍, 함수 작성 규칙을 설명합니다.
```

나쁜 예

- 배경 설명을 길게 하느라 핵심 주제가 뒤늦게 나옴
- 다른 도메인 예시부터 먼저 길게 나옴
- 제목은 일반적인데 첫 문단에서 실제 주제가 잘 안 보임

---

## 4. 폴더별 작성 규칙

### 4.1 `ansible/`

넓어야 하는 내용

- Ansible 플레이북 구조 설명
- role/task 작성 규칙
- 인벤토리 운영 문서
- Ansible 모듈 사용 가이드

넓으면 안 되는 내용

- 일반 Python 스타일 규칙
- 범용 코드 품질 문서
- 특정 언어 구현 예시

### 4.2 `python/`

넓어야 하는 내용

- Python 스타일 가이드 (PEP 8 등)
- 구현 규칙
- 코드 품질 기준
- 함수/클래스 작성 규칙

주의할 점

- Python specific한 내용만 담습니다.
- Ansible이나 다른 언어-specific한 내용을 섞지 않습니다.

> 현재 저장소에서 Ansible 성격 문서가 다른 폴더에 섞여 있다면, 새 문서를 추가하기 전에 먼저 **올바른 폴더 기준으로 재정렬**하는 것이 좋습니다.

---

## 5. chunk 친화적인 문서 구조 규칙

현재 chunk 크기가 비교적 크기 때문에, 문서가 한 덩어리로 너무 길어지면 관련 없는 내용이 함께 묶입니다. 아래 원칙을 지켜야 검색 품질이 좋아집니다.

### 5.1 헤딩 구조를 적극적으로 사용합니다

- H1: 문서 전체 주제
- H2: 독립적으로 검색될 수 있는 작업/질문 단위
- H3: 세부 규칙, 예외, 변형 케이스

좋은 예

- `## 함수 네이밍 규칙`
- `## 플레이북 task 작성 순서`
- `## 예외 처리 기준`

나쁜 예

- 헤딩 없이 긴 문단만 이어짐
- 서로 다른 주제가 하나의 H2 아래에 계속 섞임

### 5.2 문단은 짧고 명확하게 나눕니다

- 한 문단에 하나의 핵심 주장만 둡니다.
- 매우 긴 설명은 2~4개 문단으로 나눕니다.
- 리스트/표/코드블록만 두지 말고, **그 앞이나 뒤에 설명 문장**을 둡니다.

### 5.3 코드블록과 예시는 설명과 붙여 둡니다

예시 코드만 덩그러니 두면 검색 시 의미가 약해집니다.

좋은 예

```md
## 함수 네이밍 예시

아래 예시는 동사 중심 함수명을 사용하는 패턴을 보여줍니다.

```python
def load_inventory():
    ...
```
```

## 6. 제목, 첫 문단, 키워드 규칙

### 6.1 제목은 실제 검색어에 가깝게 씁니다

- 애매한 파일명보다 **주제가 드러나는 파일명**을 사용합니다.
- 파일명과 제목은 서로 너무 멀어지지 않게 맞춥니다.

좋은 예

- `python_function_style.md`
- `ansible_role_structure.md`
- `nginx_playbook_example.md`

나쁜 예

- `정리.md`
- `예제1.md`
- `구조.md`

### 6.2 첫 문단에는 아래 요소를 넣습니다

- 이 문서가 다루는 주제
- 누가 언제 참고하는 문서인지
- 실제 질의에 쓰일 키워드 2~5개

권장 템플릿

```md
이 문서는 [주제]를 설명합니다.
주로 [언제/누가] 참고하며, 핵심 키워드는 [키워드1], [키워드2], [키워드3]입니다.
```

### 6.3 동의어와 한글/영문 용어를 같이 둡니다

현재 검색은 완전한 의미 이해보다 키워드/표현 매칭에도 영향을 받습니다.

예시

- `Python / 파이썬`
- `Playbook / 플레이북`
- `Type Hint / 타입 힌트`

---

## 7. 혼합 도메인 누수 방지 규칙

이 저장소에서는 이 규칙이 특히 중요합니다.

### 7.1 서로 다른 도메인을 한 문서에 섞지 않습니다

예를 들어 아래 조합은 분리해야 합니다.

- Python 코드 스타일 + Ansible 플레이북 구조
- 일반 구현 규약 + 서버 운영 절차
- 예시 코드 + 운영 정책 설명

### 7.2 공통 개념이 필요하면 링크로 연결합니다

한 문서 안에 다 우겨 넣지 말고:

1. 도메인별 문서를 따로 씁니다.
2. 마지막에 `관련 문서` 섹션으로 연결합니다.

예시

```md
## 관련 문서

- `../ansible/ansible_role_structure.md`
- `../python/python_function_style.md`
```

### 7.3 잘못된 폴더에 넣은 문서는 새 문서 추가 전에 먼저 정리합니다

이미 잘못 들어간 문서가 있으면, 새 문서를 계속 쌓기 전에 **폴더 재배치 또는 파일 분리**부터 하는 편이 좋습니다.

---

## 8. 지원 파일 형식 규칙

현재 v1에서 인덱싱되는 형식은 아래뿐입니다.

- `.txt`
- `.md`
- `.html`
- `.yml`
- `.yaml`
- `.py`

지원하지 않는 형식은 넣어도 검색되지 않습니다.

특히 아래에 주의합니다.

- 이미지/PDF만 있는 문서에 핵심 설명을 넣지 않습니다.
- 표만 있는 문서는 피하고, 문장 요약을 함께 둡니다.
- HTML은 텍스트 추출 후에도 의미가 남도록 구조를 단순하게 유지합니다.

---

## 9. 작성 전 체크리스트

새 문서를 추가하거나 크게 수정하기 전에 아래를 확인합니다.

- [ ] 이 문서는 한 핵심 주제만 다루고 있는가?
- [ ] 폴더와 실제 내용의 도메인이 일치하는가?
- [ ] 제목만 보고도 주제를 알 수 있는가?
- [ ] 첫 문단에서 문서 정체와 핵심 키워드가 드러나는가?
- [ ] 헤딩 구조가 명확한가?
- [ ] 너무 긴 문단/혼합 주제가 없는가?
- [ ] 코드/표/예시 앞뒤에 설명 문장이 있는가?
- [ ] 현재 지원 파일 형식인가?
- [ ] 비슷한 문서가 이미 있는데 중복으로 또 추가하는 것은 아닌가?
- [ ] 관련 문서가 있다면 링크로 연결했는가?

---

## 10. 리뷰어 체크리스트

리뷰할 때는 아래 항목을 봅니다.

1. 폴더 위치가 맞는가?
2. 첫 문단만 읽어도 주제를 알 수 있는가?
3. 다른 도메인 내용이 섞여 있지 않은가?
4. chunk가 너무 길어질 만큼 문단/섹션이 비대하지 않은가?
5. 제목·파일명·헤딩이 실제 검색어와 동떨어지지 않는가?
6. 예시가 설명 없이 혼자 떠 있지 않은가?

## 11. 빠른 예시

### 좋은 예

- `python/Python 코드 스타일 가이드 (PEP 8).md`
  - 첫 줄부터 Python 스타일 문서라는 정체가 드러남
  - 초기 키워드가 강함
  - 헤딩 구조가 비교적 명확함

### 나쁜 예

- `python/Ansible Playbook 계층 구조.md`
  - 폴더는 `python`인데 실제 내용은 Ansible Playbook 구조 설명
  - 현재 RAG 기준으로는 Python 질의에도 섞여 나올 위험이 있음

---

## 12. 결론

현재 AnsibleHarness의 knowledge_base는 자유 문서 저장소가 아니라, **검색 품질을 위해 의도적으로 구조화해야 하는 RAG 말뭉치**입니다.

따라서 가장 중요한 원칙은 아래 세 가지입니다.

1. **한 파일에는 한 주제만 쓴다.**
2. **폴더 의미와 실제 내용을 반드시 맞춘다.**
3. **제목과 첫 문단에서 문서 정체를 바로 선언한다.**

이 세 가지만 지켜도 지금 시스템에서 검색 누수와 혼합-domain 문제를 상당 부분 줄일 수 있습니다.
